# 技术方案评审 / 架构分析类 PPT 版式演进方案

## 范围与边界

- 样本来源：主要参考 `/Users/guoshuaiqi/Documents/模板文件 2/` 中的第二批真实业务 PPT 照片，并结合 `REAL_PPT_VISUAL_ANALYSIS.md` 已归纳的第二批对比结论。
- 本轮只分析版式与结构，不解析照片、不修改代码、不修改 IR 契约。
- 照片可能包含真实业务内容，本报告只保留结构性描述；具体项目名、数字、客户、人员与业务结论均以 `<占位>` 表示或直接省略。
- 照片拍摄条件会影响颜色、字体和比例判断，因此本报告不推断精确色值、字体名或 CI 规范，只做方向判断。

## 1. 技术评审 / 架构类页面类型

### 1. 封面 / 技术专题首页

- 代表图：`IMG_0422`
- 结构特征：大幅背景图或题图占主视觉，标题位于左上或中上区域，角落有品牌标识，底部可能有作者、日期、密级、组织等元信息。
- 内容密度：低。
- 版式作用：建立专题、会议或评审对象。

### 2. 目录 / 评审路径页

- 代表图：`IMG_0424`
- 结构特征：左侧或上方大标题，正文为 3-5 条议程；留白较多，通常带品牌标识或页脚。
- 内容密度：低到中。
- 版式作用：给出评审顺序、问题域或章节路径。

### 3. 评审结论 / 背景摘要 / 问题框定页

- 代表图：`IMG_0423`、`IMG_0453`、`IMG_0454`
- 结构特征：页面顶部标题，下方是分组短段落、项目符号、强调语句或小表；常见红色/蓝色局部强调，但照片无法精确判断颜色规范。
- 内容密度：中到高。
- 版式作用：说明为什么评审、当前结论、关键约束、已确认问题或待解决问题。

### 4. 需求背景 / 里程碑 / 范围说明页

- 代表图：`IMG_0425`、`IMG_0429`、`IMG_0430`
- 结构特征：时间线、阶段节点、范围说明、小表格和关键说明混排；常见横向时间轴或阶段块。
- 内容密度：中。
- 版式作用：解释需求来源、阶段目标、版本节奏或评审范围。

### 5. 性能目标 / 指标概念页

- 代表图：`IMG_0426`
- 结构特征：中心是三角、环形、分层或关系图；左右或下方配少量说明文字；强调目标、约束、指标之间的关系。
- 内容密度：中。
- 版式作用：把技术目标、性能指标或评价维度抽象成概念框架。

### 6. 架构框图 / 模块分层页

- 代表图：`IMG_0433`、`IMG_0437`、`IMG_0450`、`IMG_0467`
- 结构特征：大量矩形节点、分组框、层级关系、箭头、左右/上下分区；常见“左侧说明 + 右侧架构图”或“两套方案并排比较”。
- 内容密度：高。
- 版式作用：表达系统模块、逻辑分层、方案结构和模块职责。

### 7. 信道 / 数据流 / 调用链示意页

- 代表图：`IMG_0441`、`IMG_0443`、`IMG_0444`、`IMG_0449`、`IMG_0458`
- 结构特征：有方向箭头、泳道、上下游节点、步骤编号或信号流向；比普通架构图更强调顺序、路径和交互。
- 内容密度：高。
- 版式作用：说明数据如何流动、模块如何协同、某条链路如何闭环。

### 8. 方案对比表 / 决策矩阵页

- 代表图：`IMG_0434`、`IMG_0435`、`IMG_0438`、`IMG_0451`
- 结构特征：大表格为主，列通常是方案、维度、收益、影响、风险或结论；有些单元格内嵌小图、短列表或重点标记。
- 内容密度：高。
- 版式作用：支持技术路线选择、方案取舍和评审拍板。

### 9. 指标 / 性能图表页

- 代表图：`IMG_0456`、`IMG_0457`、`IMG_0459`、`IMG_0460`
- 结构特征：折线、柱状、堆叠或趋势图为主，旁边或下方有解释文字、小表或结论标签。
- 内容密度：中到高。
- 版式作用：用数据支撑性能、稳定性、容量、质量或收益判断。

### 10. 风险 / 问题清单 / 闭环跟踪页

- 代表图：`IMG_0440`、`IMG_0466`、`IMG_0469`
- 结构特征：项目符号或表格列出问题、状态、责任、影响、措施；常见底部强调说明或风险提示。
- 内容密度：中到高。
- 版式作用：暴露未闭环事项、评审风险和后续动作。

### 11. 结束 / 致谢页

- 代表图：`IMG_0452`
- 结构特征：短标题或致谢语作为主视觉，一侧放品牌、法律、组织或声明类文本。
- 内容密度：低。
- 版式作用：会议结束和品牌收束。

## 2. 与现有 DeckIR 10 版式的差距

现有 DeckIR 版式集合为：`cover`、`agenda`、`section`、`title_bullets`、`two_column`、`table`、`cards`、`chart`、`image`、`conclusion`。

### 现有版式改造后可以承接的页面

| 页面类型 | 可承接的现有版式 | 当前差距 | 建议补充字段方向 |
| --- | --- | --- | --- |
| 封面 / 技术专题首页 | `cover` | 当前能表达标题、副标题、汇报人、日期，但不能表达题图、品牌角标、页脚信息、密级/组织块 | `hero_image_ref`、`logo_ref`、`footer_meta`、`classification` |
| 目录 / 评审路径页 | `agenda` | 能表达条目，但缺少标题层级、编号样式、右侧/底部品牌区域 | `title`、`subtitle`、`numbering_style`、`footer_meta` |
| 评审结论 / 背景摘要页 | `title_bullets` | 能表达普通要点，不能表达分组、小标题、局部强调、结论框 | `sections`、`emphasis_runs`、`callout`、`severity` |
| 风险 / 问题清单页 | `title_bullets` 或 `table` | 简单风险清单可表达，状态、负责人、风险等级、闭环动作需要结构化 | `status`、`owner`、`severity`、`action`、`due_hint` |
| 方案对比表 / 决策矩阵页 | `table` | 普通文本表可表达，但缺少分组表头、合并单元格、重点单元格、单元格内短列表/小图 | `row_groups`、`column_groups`、`cell_spans`、`cell_blocks`、`highlights` |
| 指标 / 性能图表页 | `chart` | 当前 chart 只适合基础图表；真实页常有多图、阈值线、单位、注释、侧边结论和小表 | `panels`、`unit`、`thresholds`、`annotations`、`side_notes`、`side_table` |
| 结束 / 致谢页 | `conclusion` | 能表达结束要点，但缺少大字致谢、品牌/法律声明块 | `closing_text`、`brand_block`、`legal_text` |

这些页面不一定需要新增顶层 layout，可以先通过增强现有 layout 字段承接。但这属于 IR 契约演进，不能在当前契约不变的前提下直接实现。

### 现有版式难以表达、需要新增或引入新抽象的页面

| 页面类型 | 为什么现有版式不够 | 建议方向 |
| --- | --- | --- |
| 架构框图 / 模块分层页 | `two_column` 只能放文字，`image` 只能放静态图，`chart` 不是节点连线语义；无法表达模块、分组、层级、箭头和连线方向 | 新增 `architecture_diagram`，底层引入节点、边、分组、泳道、布局策略 |
| 信道 / 数据流 / 调用链示意页 | 需要表达顺序、方向、泳道、路径、链路标签和跨层交互；普通表格或要点页会丢失核心语义 | 新增 `flow_diagram` 或让 `architecture_diagram` 支持 `flow` 模式 |
| 性能目标 / 指标概念页 | 多为中心关系图、三角/环形/分层结构，不是传统数据图表 | 可新增轻量 `concept_diagram`，或纳入通用 diagram 抽象 |
| 需求背景 / 里程碑 / 范围说明页 | 真实页常是时间线 + 小表 + 说明的组合；现有 `section` / `title_bullets` 只能近似 | 可新增 `timeline_briefing`，也可先用增强 `title_bullets` + `table` 组合过渡 |

## 3. 架构 / 模块框图页专项评估

### 当前能力能否近似

可以近似，但只是“看起来有一页”，不是可用的架构表达：

- 用 `image`：可以放一张占位图或人工绘制后的截图，但 IR 不知道图中有哪些模块、连线和分组，后续无法检查、修改或复用。
- 用 `two_column`：可以左侧写说明、右侧放占位描述，但无法生成真实节点连线。
- 用 `table`：可以勉强表达模块清单或矩阵，不能表达拓扑关系。
- 用 `chart`：语义不匹配，容易把结构图错误降级成数据图。

因此，现有 DeckIR 只能近似表达“架构图页的文字外壳”，不能真正表达“架构图本身”。

### 真正支持需要的抽象

建议未来新增通用 diagram 能力，架构图和数据流图共享底层结构：

- `nodes`：节点 id、标题、类型、所属分组、层级、状态、简短说明、可选位置提示。
- `edges`：起点、终点、方向、标签、线型、重要性、可选路径提示。
- `groups`：分组 id、标题、类型、布局方向、包含节点、视觉边界。
- `lanes`：泳道或层级，用于系统层、模块层、数据层、外部依赖等结构。
- `annotations`：局部说明、风险标记、关键路径标记。
- `layout_strategy`：分层 DAG、左右流向、上下流向、泳道、网格、方案并排比较。
- `manual_hints`：允许保留人工微调锚点，避免自动布局每次生成结果漂移。

### 自动生成可用性判断

架构框图从自由文本自动生成到“可直接交付使用”不现实。原因是：

- 技术文本经常省略隐含关系，模型难以确定模块边界和真实依赖方向。
- 复杂图的节点摆放、连线路由、避免重叠、对齐和局部强调高度依赖人工审美与业务语义。
- 真实评审页里的框图常同时承担说明、对比、强调和结论功能，不只是拓扑图。

更现实的目标是：

- P1：生成结构化骨架，包含节点、分组、方向和主要连线，做到“能作为初稿继续编辑”。
- P1/P2：提供少量固定模板，如分层架构、左右数据流、两方案对比、模块调用链。
- P2：加入布局回路和 lint 检查，减少重叠、越界、对齐错误。
- 人工仍需确认模块语义、关键连线、布局观感和最终交付效果。

## 4. 分期建议

### 第一优先：方案对比表 / 决策矩阵

- 理由：在技术评审中高频出现，直接服务“拍板”；实现难度低于架构图；现有 `table` 已有基础，增强字段后收益明显。
- 建议做法：先把普通表格升级为可表达分组表头、重点单元格、单元格内短列表和结论列的结构化表。
- 交付价值：能覆盖方案选择、风险收益对比、影响分析、结论汇总等多类页面。

### 第二优先：指标 / 性能图表页

- 理由：同样高频，且现有 `chart` 已有基础；技术评审需要用数据支撑结论。
- 建议做法：增强 chart 为“图表 + 结论 + 阈值/注释 + 小表”的 performance panel，而不是只画一个孤立图。
- 交付价值：能覆盖性能、容量、稳定性、质量趋势等页面。

### 中期投入：架构框图 / 数据流图骨架

- 理由：价值最高，但实现难度也最高；需要新增节点、边、分组和布局抽象。
- 建议做法：先只做骨架型 `architecture_diagram`，限制节点数量和模板类型，强调可编辑初稿，不承诺一次生成可交付图。

### 延后或半成品：复杂架构图全自动生成

- 理由：真实样本中的架构页密度高、语义强、布局复杂，自动生成要同时解决业务正确性和视觉质量，投入很大。
- 建议策略：明确作为 P2/P3，不应作为近期验收主线；近期只承诺骨架、占位和人工可调。

### 低成本顺手优化：封面、目录、结束页

- 理由：实现简单，但对技术评审核心价值较低；现有 `cover`、`agenda`、`conclusion` 已能粗略覆盖。
- 建议策略：作为主题和品牌层的补齐项，不抢占对比表、图表、架构骨架的优先级。

## 5. 仍缺的素材与外部输入

要把上述设计精确落地，还缺以下输入：

- 源 PPTX：照片只能看结构，无法确认真实尺寸、母版、字体、色值、图层和对象类型。
- CI / 模板规范：需要官方主题色、字号层级、页眉页脚、logo、密级、免责声明等规则。
- 更多同类样本：尤其是完整技术评审链路，从封面到结论的连续 deck，而不是单页照片集合。
- 架构图源对象：需要真实 PPTX 中的可编辑形状，判断这些图是手工图、SmartArt、图片还是插件生成。
- 指标图原始数据：需要表格数据或图表对象，才能验证 chart IR 是否能复现真实图表。
- 业务术语字典：架构节点类型、模块层级、信道/接口/数据流名称需要领域词表，否则自动生成容易产生错误结构。
- 人工视觉终审标准：照片只能支撑方向分析，最终“是否像真实华为技术评审材料”仍需人工在源 PPTX 或 Windows 环境下验证。

## 6. 落地结论

- 技术评审 / 架构分析类 PPT 至少可细分为 11 种页面类型。
- 现有 10 版式能覆盖外壳最多的是封面、目录、结论、普通要点、普通表格和基础图表。
- 最关键的缺口是结构化技术图：架构框图、数据流图、调用链图、概念关系图。
- 近期最值得做的是增强 `table` 承接方案对比矩阵，以及增强 `chart` 承接性能指标页。
- 架构框图应作为中期核心能力，但目标应定为“生成可编辑骨架 + 人工调优”，不应承诺从文本自动生成到直接可交付。
