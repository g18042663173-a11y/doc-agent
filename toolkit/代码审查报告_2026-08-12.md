## 一、最严重的问题（✅ 已人工复核）

### 1. CRITICAL｜NGA HTTP 传输配置在桌面端永远保存失败 ✅

**跨端确认：Python agent 与 C# agent 独立发现同一问题。**

- `backend/app/web_api.py:580` — `_nga_config_from_payload` 对 HTTP 分支直接把整个 `config_payload` 传给 `NgaHttpConfig.model_validate()`
- `backend/app/generators/nga.py:40-52` — `NgaHttpConfig` 配置 `extra="forbid"`，且**没有** `transport` / `cli_path` 字段
- `desktop/DocumentWorkbench/SettingsStore.cs:95-96` — C# 端 `NgaStoredConfig` **总是**序列化 `transport` 和 `cli_path`（默认 `cli_path="nga"`）

**后果**：C# 前端在 HTTP 传输模式下保存/测试/激活 NGA 配置，payload 必然携带 `transport`、`cli_path`，pydantic 因 `extra="forbid"` 抛出 `ValidationError` → 后端返回 `E010 "NGA 配置字段无效"`，HTTP 传输配置功能**永远无法通过桌面 UI 使用**。CLI 分支走白名单（web_api.py:571-578）所以正常。

**修复**：HTTP 分支也改为白名单构造（剔除 `transport`/`cli_path`），或给 `NgaHttpConfig` 增加 `transport: Literal["http"]` 字段。

---

### 2. HIGH｜`web_api.main()` 无会话令牌运行，整个 API 无鉴权 ✅

- `backend/app/web_api.py:1970` — `create_api_app(work_dir=args.work_dir)` 未传 `session_token`
- `create_api_app` 签名 `session_token: str | None = None`（line 913）
- `_require_desktop_session`（line 406-410）在 `session_token is None` 时直接放行

**后果**：生产模式 main 绑定 127.0.0.1:5056，但任何本机进程（或恶意网页的简单跨源 POST，multipart 表单无 CORS 预检）都可调用 `/api/generate`、`/api/analyze` 等接口，造成队列/磁盘 DoS。桌面模式（`desktop_host.py`）走的是正确的令牌守卫，两者行为不一致。

**修复**：在 `main()` 生成并校验令牌（镜像 `desktop_host` 的 bootstrap 逻辑），或仅当显式传入 `--no-auth` 开发标志时才允许无令牌。

---

### 3. HIGH｜xlsx 解析器对同一个 read-only worksheet 迭代两次 ✅

- `backend/app/parsers/xlsx_parser.py:56,70,80,125` — `value_workbook = load_workbook(path, read_only=True, ...)`；`sheet = value_workbook[sheet_name]` 同时传给 `_preview_rows`（line 282 `iter_rows`）和 `_column_stats`（line 364 `iter_rows`）
- openpyxl read-only worksheet 是**单次遍历**：底层 zip 流被消费。`_preview_rows` 提前在 20 行 break 后，`_column_stats` 从中断位置继续（得到的是第 21 行起的错误数据，隐藏行过滤和 `non_empty_ratio` 全错）；≤20 行的 sheet 流耗尽后第二次迭代直接返回空，`col_stats` 为空或抛错。

**修复**：一趟完成预览与列统计，或对第二次扫描重新 `load_workbook`。

---

### 4. HIGH｜C# 后端子进程管道从不排空 → 潜在死锁 ✅

- `desktop/DocumentWorkbench/BackendProcessHost.cs:58-66` — `RedirectStandardOutput/Error = true`
- 但 stderr 只在 `process.HasExited` 之后才 `ReadToEndAsync`（line 89-92），stdout **整个生命周期从不读取**

**后果**：Windows 管道缓冲只有 4–64KB。Python 进程存活期间若往 stderr 写入超过缓冲的日志（比如 job 工作线程抛异常打印 traceback），进程会**永久阻塞**在写操作上；启动期同理会拖垮 35 秒启动时限（line 85-108），误报"未在 35 秒内完成启动"。

**修复**：进程启动后立即开两个持续读取任务（`ReadLineAsync` 循环或 `BeginOutputReadLine/BeginErrorReadLine`）。

---

### 5. HIGH｜主题名未校验可读任意本地 JSON ✅

- `backend/app/rendering/theme.py:32-37` — `load_theme(name)` 直接拼 `THEMES_DIR / f"{name}.json"`，未走 `THEME_REGISTRY`/`resolve_theme`
- 调用方 `cli/check.py:25`、`prompting/builder.py:684`、`lint/pptx_lint.py:68` 传入的 `theme` 仅受 `max_length=64` 约束

**后果**：`../../...` 路径穿越可读取磁盘上任意 `.json`，其 `style_guide` 内容被**原样注入 LLM prompt** 并出现在生成产物里，形成本地文件外带通道。web API 路径被 `_theme_from_form` 缓解，但库函数本身不安全。

**修复**：读路径前先 `resolve_theme(name)` 或校验 `name in THEME_REGISTRY`。

---

### 6. MEDIUM｜Office 包 DTD/ENTITY 字节扫描可被 UTF-16 绕过 ✅

- `backend/app/security/office_package.py:191-206` — `_scan_xml_safety` 对原始字节做 ASCII 子串匹配 `<!doctype`/`<!entity`
- ECMA-376 允许 XML 部件使用 UTF-16 编码，此时 `<!ENTITY` 存储为 `<\x00!...`，完全不匹配

**后果**：这是传给 python-docx/python-pptx 前的**主要防线**，UTF-16 编码的恶意 DTD/ENTITY 可绕过前置检查（是否最终变成 XXE 取决于下游 lxml 解析设置）。

**修复**：按 XML 声明/BOM 解码后再扫描，或同时匹配 UTF-16LE/BE/UTF-32 字节模式。
